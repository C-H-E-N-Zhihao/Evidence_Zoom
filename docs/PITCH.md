## The 3-minute talk (spoken over the live app; approved in `andrew-talk-signoff`)

Rehearsed order and timings from the Mac live check (message 243). Model replies take about 3–8 s each.

**0:00–0:25 · Problem.** "A customer sends a support bot a photo, a receipt or a claim form, and asks a question. The usual approach sends the whole high-resolution image to a large vision model, every time. That is the expensive path, and the answer doesn't show where it came from."

**0:25–0:50 · Idea.** "Evidence Zoom sends the model as little of the image as it can, cheapest step first.
- OCR runs on the device, for free.
- On an unfamiliar receipt we try a small image. If the proposed answer appears in the local OCR text, we can stop. Otherwise the app can request more detail or flag the question for review.
- On a form we know, the form's own layout picks the crop.
- Every answer shows its evidence on the image: the OCR line it read, or the image region sent to the model. If it can't answer, it flags the question for human review, with a ready ticket."

**0:50–2:05 · Live demo** (`./scripts/demo-live.sh`; fallback `./scripts/demo.sh`, labelled replay):
1. Upload a receipt photo and ask "What is the total amount?" The answer shows "✓ found in the page text", a green box on the line, and the token pill against the original photo. *(20 s)*
2. Ask "What is the customer's loyalty number?" The app says "Human review needed"; click **Create ticket**. Do not say that no larger image is sent: in the live check it sent one before flagging. *(15 s)*
3. Pick "Accident claim form #2" and wait 2–3 s for it to appear. Ask the policy number: read by OCR, 0 model tokens. Ask driver B's ticks: answered from a narrow crop picked by the layout. Switch to **version B**: one tick moved, and the answer and box move with it. *(30 s)*
4. The savings card: the session's tokens against sending the original images. *(10 s)*

**2:05–2:40 · Result.** "We ran the app with its shipped defaults on 60 fresh receipt photos that nothing was tuned on: 248 questions. It answered 188 correctly, flagged all 60 unanswerable questions for review and gave no wrong answers. That took 968 provider tokens per correct answer, against 2,740 for sending the photo to the same model: 65 % fewer. 31 answers needed no model call at all. Haiku, one paired run."

**2:40–3:00 · Limits, then close.** "We kept the negatives. On layouts we haven't configured there is no region selection: it reads a smaller whole page. And the OCR check confirms an answer is printed, not that it answers the question. With open models that let more wrong answers through. Evidence Zoom: frugal by default, checkable by design."

*Optional, if time allows:* "On receipts our trained pointer found the annotated field more often than a random guess, but the OCR-checked route answered more questions correctly with fewer model tokens, so that's what we shipped."

| "Does it make things up?" | On the clean run, OCR answered 48/96 [dev] questions correctly with 0 wrong. On missing fields, 72B declined 12/12 on the route, while 7B invented a value in 2/12. On layout 2, our first fallback invented missing fields, so router v2 sends the page instead. In the live check, Haiku declined a missing-field question and an off-script question; do not promise it always will. | NARRATIVE §3, message 088 |
| "Why not just find the text the question names and crop around it?" | We tried it, on development examples only, so this is exploratory. On row checklists (accident circumstances, numbered travel questions) the matched rows fit in a narrow band around the named phrase. Elsewhere it does not work: many questions name no item, and the evidence is often away from its label, e.g. a breaker switch far from its legend, or a damage mark on a diagram while the name is in the key. A generic window would give partial crops, which we treat as worse than sending the page, so it is not in the router. Do not claim the reader answered correctly, or that all travel rows were found. | message 132; approved for presenter notes in andrew-release-review-133-139 (b9a8ef9) |

| "Does this only work for insurance forms?" | No. The app now takes any image: OCR runs locally first, configured forms get region crops, and any other image goes to the model as a small page cropped to its OCR text area; if the answer is not in the OCR text, a sharper page follows (see the real-documents answer). An earlier text-first assistant, no longer used by the app, was tested on homework worksheets: the model first got only the OCR text, and pixels only when it asked. On a first blind set the route lost (83/96 vs 94/96 for the whole page). We fixed the crop and tested a second blind set: 96/96 vs 95/96 at about 70 % of the API charge, with no image sent for 44 of 48 text questions. Synthetic worksheets; the two runs changed both the route and the data, so do not claim the fix alone did it, or that the route is more accurate. | NARRATIVE §3 (c5822d3), andrew-general-v2-review |
| "Does it work on real documents, not your synthetic forms?" | We tested public benchmarks (DocVQA scans, infographics, charts; new questions each time). There the OCR-text-first route was slightly cheaper ($0.061 vs $0.069 for 210 questions) but less accurate: the whole page scored DocVQA ANLS 0.951 vs 0.900, InfographicVQA 0.761 vs 0.619, and six more correct overall on the substring score; the route led only on ChartQA (33 vs 31 of 70). So the app no longer reads OCR text first: for any image without a configured layout it sends the page as one image. What does save money on real scans is the **page size**: at 1024 px, whole-page Haiku had the same mean score on 70 DocVQA questions as full size, at about one-third of the API charge. Infographics lose accuracy at every smaller size. The app crops the page to where OCR found text, asks on a small version first, and keeps the answer only if it appears in the local OCR text; otherwise a sharper page follows. Measured as shipped: on 248 questions about 60 held-out receipt photos, 968 vs 2,740 tokens per correct answer against the original photo (188 vs 187 correct, 0 vs 1 wrong); on 100 DocVQA scans, 1,574 vs 4,587 against a separately prompted original page (both 96 correct, ANLS 0.920 vs 0.931). The model-free router savings remain for configured forms. | NARRATIVE §3, `eval/results/REPORT_realdocs.md`, andrew-review-172, andrew-review-resolution; audit 178; andrew-review-final-cord, andrew-review-ladder |
